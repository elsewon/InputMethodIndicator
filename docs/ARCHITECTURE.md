# 아키텍처

InputMethodIndicator는 macOS에서 입력 캐럿 아래에 표시되는 입력 상태 표시기의
복제품이다. 작업 표시줄 트레이의 입력 상태가 바뀌면(한/영 또는 Caps Lock) 캐럿 바로
아래에 캡슐을 띄운다. **단일 자립형 `InputMethodIndicator.exe`**이며, UI 스레드 하나와
프로세스 경계를 넘는 UIA 작업을 맡는 작업자 스레드 셋(트레이 감시자, 캐럿 해석기,
포커스 감시자)으로 동작한다.

## 핵심 아이디어

Windows는 이미 **트레이 입력 표시기**를 통해 참 입력 상태를 노출한다. 그 표시기는
`Shell_TrayWnd` 아래의 UI Automation 요소(`autoId=SystemTrayIcon`,
`class=SystemTray.NormalButton`)이며, 접근성 **Name**이 `"트레이 입력 표시기 한국어
입력 모드"` / `"…영어 입력 모드"`(영어 UI: `"… Korean/English input mode"`) 같은
현지화된 문자열이다. 한/영을 토글할 때마다 바뀌면서 `UIA_NamePropertyId`
property-changed 이벤트를 일으킨다. 그 요소를 읽는 것이 전부다.

## 구성 요소

```
InputMethodIndicator.exe (x64) — UI 스레드 + UIA 작업자 스레드 셋

  TrayIndicatorWatcher ──(UIA Name 변경)──► InputStateMachine ──(emit)──► App
    (SystemTrayIcon을 찾고                     (디바운스, 앱 전환               │
     Name 이벤트를 구독)                        유예, 게이팅)                   ▼
                                                                  CaretResolver ─► OverlayWindow
  CapsLockMonitor ──(WH_KEYBOARD_LL)──► InputStateMachine          (캐럿 사각형)    (D2D 캡슐)

  foreground + focus WinEvent 훅 ──► App (캐럿 대상, 유예 구간, 포커스 캡슐)
  TrayIcon (고정 IMI)   Config (HKCU)   Diagnostics (로그 + 뷰어)
```

- **TrayIndicatorWatcher**는 전용 MTA 작업자 스레드에서 `IUIAutomation`
  클라이언트를 만들고, 한 번의 대량 `FindAll`(AutomationId `SystemTrayIcon`,
  Name은 같은 프로세스 간 호출에서 미리 캐시된다)로 표시기를 찾는다. id가 언젠가
  바뀌면 raw-view 깊이 우선 탐색으로 대체한다. 약 4초 주기의 작업자 재검증 틱이 explorer
  재시작 이후 구독을 다시 걸고 최선 칩을 **신선하게 다시 찾아** 상태 표류를
  바로잡는다(부재가 이어지면 백오프한다). 그래서 구독이 실패해도 침묵으로
  떨어지는 대신 폴링으로 성능이 저하될 뿐이다. 표시기를 오래(느린 탐색으로) 읽지
  못하면 — explorer 접근성 트리 이상의 신호다 — 호스트에 건강 상태를 알려 트레이
  풍선 알림(`Shell_NotifyIcon` `NIF_INFO`; 셸이 토스트로 표시한다. WinRT 토스트
  API는 자립형 exe에 필요한 AUMID/바로가기 신원 없이는 못 쓰므로 쓰지 않는다)으로
  사용자에게 explorer 재시작을 안내하고, 회복 시에도 한 번 알린다 (전이당 한 번). 정상적으로 부재한 경우는 탐색이 빠르므로 알리지 않는다. 그
  알림 본문을 클릭하거나 트레이 메뉴의 항목을 고르면 확인 대화상자 뒤에 탐색기를
  재시작하고, 재시작으로 셸이 트레이 등록을 잃으면 `TaskbarCreated`를 받아 아이콘을
  다시 등록한다.

  입력기가 2개 이상이면 언어로 파싱되는 칩이 **둘**이다: 변환 모드 칩
  (`…한국어/영어 입력 모드`, 한/영 토글마다 rename)과 입력기 전환 칩
  (`…한국어\nMicrosoft 입력기…`, 입력기 변경 시 rename). 한/영 상태의 출처는
  모드 칩이므로 탐색은 모드 칩을 우선한다(`IsTrayModeIndicatorName`).

  Name 변경 구독은 개별 칩이 아니라 **트레이 루트에 서브트리 범위**로 건다.
  모드 칩은 입력기 전환마다 파괴되고 다른 runtime id로 재생성되므로 칩 단위
  구독은 그 순간 조용히 죽고, 더 나쁘게는 파괴된 칩이 `get_CurrentName`에 마지막
  Name으로 계속 답하기 때문에(좀비) 생존 검사로는 알아챌 수 없다. 그래서 이벤트
  앵커는 전환에도 살아남는 루트로 하고, 탐색은 캐시된 포인터를 신뢰하지 않는다. 핸들러 규칙: 모드 칩 rename은 즉시 post하고, 전환 칩 rename은 작업자에
  재탐색을 신호한다 — 작업자는 새 모드 칩이 생성되길 잠시 기다렸다가(~450 ms)
  현재 상태를 **methodSwitch**로 post하며, 상태 머신은 보이는 언어가 같아도
  (입력기 왕복 후 한국어 IME는 영어(A) 모드로 리셋된다) 캡슐을 띄우고 유예 구간도
  무시한다(전환 칩은 입력기가 실제로 바뀔 때만 rename되므로 구조상 사용자
  행동이다).

  이 모든 것이 작업자 스레드에 있는 이유: 탐색/재검증은 explorer를 상대로 한
  **동기 프로세스 간 호출**의 연속이라 수백 ms~수 초씩 걸릴 수 있다 — 특히
  표시기가 없는 기계(입력기 하나뿐, 표시기 숨김, 낯선 셸 빌드)에서는 전체 깊이
  우선 탐색이 재검증마다 실패를 반복한다. UI 스레드는 LL 키보드 훅과 트레이 메뉴를 소유하므로
  거기서 블로킹하면 시스템 **전역** 입력 지연과 메뉴 멈춤이 된다.
- property-changed 핸들러는 **아무런** UIA 호출도 하지 않고(새 Name은 이벤트
  VARIANT 안에 들어 있다) UIA 스레드 풀 스레드에서 실행된다. Language를 파싱한 뒤
  트레이 창으로 `PostMessage`할 뿐이다 — 그 post가 곧 UI 스레드로의 마샬링이므로,
  콜백은 결코 블로킹되지 않고 무거운 경로는 메시지 루프에서 돈다.
- **InputStateMachine**은 언어/caps 이벤트를 결정으로 바꾸며, 시작 시 동기화,
  중복 상태, 빠른 반복, 그리고 — 포어그라운드 훅이 여는 짧은 유예 구간을 통해 —
  앱 전환 시 트레이의 창별 동기화를 억제한다(그래서 모드가 다른 창들 사이를
  alt-tab 해도 캡슐이 번쩍이지 않는다). LL 훅이 기록한 언어 토글 키 입력(한/영,
  `VK_IME_ON/OFF`, Win+Space)이 지난 500 ms 안에 있으면 **유예 구간을 무시**한다.
  그래서 앱 전환 직후의 진짜 토글은 여전히 보인다.
- **CaretResolver**는 캐럿 사각형을 물리 화면 픽셀 단위로 해석한다:
  `GetGUIThreadInfo` → MSAA `OBJID_CARET` / IA2 캐럿 소유자 → UIA
  `GetCaretRange` → 삽입 지점 앞의 텍스트 런 측정(Win11 XAML 상자에서 캐럿을 찾는
  유일한 방법이다. 이들은 degenerate 범위에 대해 아무것도 보고하지 않는다) →
  포커스 요소의 경계. 이 중 무엇도 답하지 못하면 **캡슐을 보여 주지 않는다**:
  표시기는 정확히 놓을 수 있는 자리에만 그려지므로, 놓을 수 없는 캡슐은 근사하지
  않고 버린다.

  IA2 단계는 UIA와 **중복이 아니다**: Chromium은 *빈* 필드의 플레이스홀더를 문서
  텍스트로 노출하고, UIA 캐럿을 그 끝에 보고한다 — 텍스트 끝의 진짜 캐럿과
  구별할 수 없다. 진실은 오직 **IAccessible2 캐럿 소유권**을 통해서만 보인다:
  `get_caretOffset`은 캐럿을 실제로 쥐고 있는 노드에서만 `S_OK`로 답한다. 자손
  텍스트 노드가 그것을 소유하면 ⇒ 그 문자 범위가 곧 캐럿이다. 자손이 아무것도
  소유하지 않은 채 컨테이너만 주장하면 ⇒ 그 내용은 장식(플레이스홀더)이고,
  타이핑은 그 첫 자식의 왼쪽 가장자리에서 시작된다. 반대로 XAML은 MSAA 캐럿도
  IA2도 노출하지 않으므로 오직 UIA 단계로만 도달할 수 있다 — 어느 쪽 스택도
  다른 쪽을 포섭하지 않으며, 그래서 둘 다 체인에 들어 있다.

  1단계(`GetGUIThreadInfo` — 대상의 협조가 필요 없는 커널 호출)만 UI 스레드에서
  인라인으로 실행되고, 2단계 이후(MSAA/IA2/UIA — 전부 포커스된 앱이 응답해야
  돌아오는 프로세스 간 동기 호출)는 전용 MTA 작업자에서 **비동기로** 실행된다:
  UI 스레드는 요청을 큐에 넣고 자신의 메시지 루프로 돌아가고, 작업자는 답이
  준비되면 `kMsg_CaretResolved`를 post한다. 대신 작업자를 기다리면 해석이 끝날
  때까지 UI 스레드가 얼어붙는다 — 오버레이 애니메이션이 멈추고, 큐에 쌓인
  WinEvent가 버려질 수 있으며, 바쁜 대상 앱이 우리 LL 키보드 훅(=시스템 전역
  입력)까지 세운다.

  **500 ms** 워치독 타이머가 대기 시간을 제한한다. 예열된 공급자는 수십 ms에
  답하지만, 갓 시작된 앱에 대한 *첫* 해석은 그 공급자를 깨워야 해서 수백 ms가
  걸릴 수 있다. 만료되면 캡슐을 통째로 버리므로, 너무 짧게 잡으면 표시기를 놓친다.
  `Debug` 로깅을 켜면 어느 단계가 답했고 얼마나 걸렸는지 볼 수 있다(`App: 캐럿
  단계=… …ms`).

  그 첫 캡슐마저 빠르게 하려고, 모든 포어그라운드 변경은 **답을 버리는 예열 해석**을
  실행한다: 사용자가 아직 기다리지 않는 사이에 공급자를 깨워, 나중에 실제 토글이
  예열된 경로를 타게 한다. 이 버림은 비용이 없다 — 완료의 요청 id가 어떤 대기
  중인 캡슐과도 일치하지 않고, 실제 요청은 세대(generation)로 예열분을 대체한다.

  큐에 든 요청은 대체되거나(더 새로운 요청이 생김) 그 밑에서 맥락이 바뀌면
  버려진다 — 앱 전환은 대기 중인 답을 취소한다. 그 답은 사용자가 이미 떠난 창을
  가리키기 때문이다.
- **OverlayWindow**는 Direct2D로 그리는 픽셀별 알파 레이어드 윈도우다(렌더 타깃
  DPI는 96에 고정되고, 기하는 모니터별로 스케일된다). 캡슐은 완전히 둥근 캡슐이다:
  파란 채움, 가느다란 더 밝은 테두리, 굵은 흰 글리프 하나(가 / A / ⇪), 캡션 없음
  — macOS 캐럿 근처 표시기와 같다. 튀어나오고(스케일 0.80 → 1.0, 알파 페이드와
  함께 이징) → 유지 → 페이드아웃한다. D2D 그리기는 스케일이 바뀌는 동안에만
  실행되고, 유지/페이드아웃은 캐시된 프레임을 새 전역 알파로 다시 present한다.
  **고정(sticky)** 모드(Caps Lock)에서는 튀어나온 뒤 타이머를 멈춘 채 `Hide()`가
  올 때까지 무기한 유지한다.
- **FocusWatcher**(Input/)는 UIA focus-changed 구독이며, 포커스 표시기가 켜져
  있는 동안에만 실행된다 — 아래의 focus-change 흐름을 참고한다. 구독을 걸고
  푸는 `AddFocusChangedEventHandler`/`Remove…`는 시스템 전역의 공급자들을
  구체화하는 무거운 호출이라(병든 explorer에서는 수 분까지 걸릴 수 있어) 전용
  MTA 작업자 스레드에서 실행된다.
- **CapsLockMonitor**는 입력 표시기가 Caps Lock 상태를 담지 않으므로
  `WH_KEYBOARD_LL` 훅을 유지한다. 그 에지 추적 토글이 **진실의 출처**다:
  `GetKeyState(VK_CAPITAL)`은 *호출 스레드의* 입력 큐를 기준으로 답하는데 이
  프로세스는 결코 키보드 포커스를 쥐지 않으므로, 그 토글 비트는 뒤처진다 — 다시
  조회하면 진짜 토글을 바로잡기는커녕 뒤집어 버린다(시작 시 기준선을 심는
  용도로만 쓴다). 같은 훅이 언어 토글 키(유예 구간 무시용)와 마지막 *타이핑*
  키(Caps와 순수 수식 키를 제외한 아무 키)에 타임스탬프를 찍으며, 이것이 아래의
  caps 표시기를 구동한다.

## 데이터 흐름

**언어 토글**: 사용자가 한/영을 누른다 → 트레이 Name이 바뀐다 → UIA 스레드 풀에서
property-changed 이벤트 → 파싱 → `PostMessage(kMsg_TrayLangChanged)` →
`InputStateMachine.OnLanguage` → 진짜 변경이면(시작도, 앱 전환 동기화도 아니면)
emit → `App`이 캐럿을 해석하고 캡슐을 보여 준다. 트레이 아이콘은 고정이며 여기에
관여하지 않는다.

**입력기 전환**(Win+Space, 전환 칩 클릭): 전환 칩이 rename된다 → 핸들러가
작업자에 재탐색을 신호한다 → 약 450 ms 뒤 작업자가 최선 칩을 다시 찾아 현재
상태를 `methodSwitch`로 post한다 → 보이는 언어가 같아도(왕복 후 IME는 A 모드로
리셋) 캡슐이 뜬다.

**Caps Lock**(지속형, macOS 스타일): LL 훅이 `kMsg_CapsChanged`를 post한다(즉시
반환해야 한다 — 느린 LL 훅은 Windows가 제거한다) → `OnCapsLock` → emit.
**CapsLockOn**에서는 캡슐이 *고정*으로 보이고 100 ms 폴링(`kTimer_CapsIdle`)이
시작된다: 사용자가 타이핑하는 동안(마지막 타이핑 키가 1초 미만 전)에는 캡슐이
숨고, 타이핑이 1초간 유휴이면 다시 튀어나온다. **CapsLockOff**에서는 폴링이
멈추고 캡슐이 버려진다. 언어 캡슐이나 앱 전환이 오버레이를 잠깐 가져가면, 폴링이 그
뒤에 caps 캡슐을 다시 앵커링한다.

**포커스 변경**(선택, `NotifyFocusChange`, 기본값 꺼짐): UIA focus-changed 구독인
**FocusWatcher**가 보고한다. WinEvent(`EVENT_OBJECT_FOCUS`) 훅으로는 이 일을 할 수
없다: Win11의 XAML 셸은 자기 컨트롤들 사이에서 포커스가 옮겨갈 때 WinEvent를
일으키지 않으므로, Explorer의 주소 표시줄 → 검색 상자 이동은 완전히 침묵한다 —
바로 표시기가 필요한 지점이다. UIA는 그것들을 보고하고 레거시 컨트롤도
프록시하므로, 혼자서 두 세계를 모두 커버한다.

이 이벤트는 160 ms 원샷 타이머를 다시 시작하고, 설정이 켜져 있는 동안에는
**포어그라운드 핸들러도 같은 타이머를 다시 시작한다**. 창의 필드 중 하나를 곧장
클릭해서 창을 활성화하면 FOREGROUND와 FOCUS 이벤트가 앱마다 다른 순서로 발생하고,
포어그라운드 핸들러는 오버레이를 숨긴다. 두 출처를 하나의 안정화 타이머로 접으면,
뒤늦게 온 포어그라운드 이벤트가 캡슐을 숨긴 채 남길 수 없고, 캡슐은 버스트의 마지막
이벤트 뒤에 한 번만 나타난다. (핸들러는 자신의 포어그라운드 갱신 뒤에만 타이머를
죽이므로, 스스로를 다시 트리거할 수 없다.) 타이머가 발화하면, `CaretResult::textInput`이
포커스가 텍스트를 받아들인다고 말할 때만 캡슐이 *현재* 모드를 보여 준다.

UIA 구독은 비싼 부분이라(시스템 전역의 모든 포커스 변경마다 공급자를
구체화한다), 계속 켜 두는 대신 설정과 함께 시작하고 멈춘다.

그 플래그는 어느 캐럿 단계가 성공했는지가 **아니라**, 포커스된 UIA 요소에
TextPattern(또는 Edit/Document 컨트롤 유형)이 있는지 물어 답한다 — *빈* 상자에는
찾을 캐럿도, 측정할 텍스트도 없으므로 Explorer의 검색 상자는 파일 타일과 같은
요소-경계 단계에 내려앉고, 이 둘은 오직 이 플래그로만 구분된다. 살아 있는 Win32
캐럿은 텍스트 컨트롤을 뜻하므로 이 플래그도 설정한다.

이 경로의 해석에는 더 긴 UIA 예산이 주어진다(350 ms 대 120 ms): 차가운 공급자를
깨우는 일은 키 입력 예산을 흔히 초과하고, 버려진 답은 "텍스트 필드가 아님"으로
읽힐 것이다. 캡슐은 이미 안정화 타이머로 지연되므로, 그 기다림을 감당할 수 있다.

**앱 전환**: `EVENT_SYSTEM_FOREGROUND` → `App`이 포어그라운드를 기록하고(캐럿
배치용) 400 ms 유예 구간을 연다. 그 구간 안에서 트레이가 새 창의 모드로 동기화하는
것은 토글이 아니라 조용한 기준선 갱신으로 취급된다 — 단, 언어 토글 키가 지난
500 ms 안에 눌렸다면 그것은 진짜 토글로 표시된다.

## 스레딩

| 스레드 | 소유 대상 |
|---|---|
| UI 스레드 (STA) | 상태 머신, 오버레이, 트레이, caps 훅, 포어그라운드 훅, config, 진단 뷰어 — LL 훅 때문에 결코 블로킹하면 안 된다 |
| 트레이 워처 작업자 (MTA) | 워처의 `IUIAutomation`: 표시기 탐색·구독·재검증(전부 프로세스 간 호출) |
| 포커스 워처 작업자 (MTA) | `AddFocusChangedEventHandler` 구독/해지 — 병든 explorer에서 수 분까지 걸릴 수 있다 |
| UIA 스레드 풀 | 워처의 property-changed 및 focus-changed 콜백을 전달한다(파싱 + `PostMessage`만 한다) |
| 캐럿 작업자 (MTA) | 캐럿 체인의 2단계 이후(MSAA/IA2/UIA — 전부 프로세스 간 동기 호출)와 그 `IUIAutomation` |

이 경계들은 모두 같은 방식으로 넘어간다 — 오프스레드 쪽은 할 수 있는 최소한만
하고 UI 스레드로 `PostMessage`하며, 모든 상태는 UI 스레드가 소유한다. UI 스레드는
결코 다른 스레드를 기다리며 블로킹하지 않는다.

로그 싱크(`Diagnostics::OnLogLine`)는 로거 잠금 아래 이 스레드들 중 어디에서나
실행될 수 있으므로, 결코 창을 건드리지 않는다: 뷰어는 보이는 동안 250 ms 타이머로
atomic dirty 플래그를 폴링한다.

## 언어 확장

언어 계층은 캐럿/오버레이와 독립적이다. IME를 추가하려면:

1. [InputState.h](../Model/InputState.h)의 `Language`에 값을 추가한다.
2. `ParseTrayIndicatorLanguage`에서 그 Name 토큰을(두 로케일 모두) 인식하게 한다.
3. `LanguageGlyph`에서 글리프를 부여한다.

일본어(あ)와 중국어(中)는 이미 예제로 스텁 처리되어 있다.
