# 진단 가이드

트레이에서 도구를 연다: **진단 보기…**. 실시간 상태와 스크롤되는 로그를 보여 준다.

## 상태 필드

창은 한국어다. 아래 라벨은 창이 실제로 출력하는 문자열이다.

| 필드 | 의미 |
|---|---|
| 입력 언어 / (IME 켜짐) | 현재 감지된 상태(가/A)와 네이티브 IME 활성 여부 |
| Caps Lock | 현재 토글 상태(켜짐/꺼짐) |
| 캐럿 탐지 | 마지막 배치를 만들어 낸 단계: `Win32 캐럿`(1), `MSAA 캐럿`(2), `IA2 캐럿`(3), `UIA 텍스트패턴`(4), `UIA 포커스 요소`(5). 어느 것도 아니면 ⇒ 캡슐이 전혀 없다 |
| 위치 / DPI | 마지막으로 해석된 사각형(물리 px)과 그것이 내려앉은 모니터 DPI |
| 소요 | 마지막 캐럿 해석에 걸린 시간(ms). 예열된 공급자는 수십 ms, 차가운 첫 해석은 수백 ms |
| 입력 표시기 | UIA 표시기 요소를 찾으면 `찾음`, 아니면 `못 찾음` |
| 언어 변경 횟수 | 수신한 트레이 언어 갱신 수(한/영을 토글하면 올라가야 한다) |
| 활성 창 | 포커스된 앱의 PID + exe(캐럿은 이 창을 기준으로 해석된다) |
| 이상 | 유형별 누적 카운터(캐럿 타임아웃 · 표시기 · UI 정지)와 마지막 이상 코드·경과 시간. [이상 코드](#이상-코드와-제보-순환) 참고 |

## 로그

레벨 로그(`Trace`/`Debug`/`Info`/`Warn`/`Error`). 모든 줄은 `wall-clock
타임스탬프 + 레벨 태그`로 시작한다 — 예: `2026-07-24 15:04:05.123 [WARN] …`.
그래서 링 버퍼·파일·제보 리포트 어디서든 언제·어느 심각도인지, 이벤트 간 간격이
얼마인지 읽을 수 있다. 싱크:

- 진단 창에 보이는 인메모리 링 버퍼(창이 보이는 동안 250 ms 타이머로 새로
  고쳐지며, 새 줄만 덧붙는다. 파일 로깅이 꺼져 있어도 항상 채워진다).
- `OutputDebugStringW` — DebugView / VS 출력 창에서 보인다.
- 파일 로깅이 켜져 있을 때(Config `logToFile`) `%LOCALAPPDATA%\InputMethodIndicator\imi.log`의
  선택적 파일. 시작 시 약 1 MB에서 `imi.log.old`로 회전된다. 트레이 → **로그 파일 열기**.

레벨은 `HKCU\Software\InputMethodIndicator` → `LogLevel`(0=Trace … 4=Error)로 설정한다.
타이밍 상세(캐럿 해석 소요, 재탐색 ms, 캐럿 단계)는 `Debug`(1) 레벨에서 나온다.

## 이상 코드와 제보 순환

사용 중 이상이 감지되면 앱이 안정적인 **이상 코드**로 표면화한다 — 유형별 카운터가
올라가고, 코드 태그가 붙은 `WARN` 한 줄이 로그에 남으며, 상태 창의 "이상" 줄과
마지막 이상 요약이 갱신된다(자동 감지). 카운터·로그는 파일 로깅이 꺼져 있어도 링
버퍼에 항상 쌓인다.

| 코드 | 뜻 | 유력한 원인 | 조치 |
|---|---|---|---|
| `CARET_TIMEOUT` | 캐럿 해석이 예산(500 ms)을 넘겨 그 캡슐을 버림 | 차가운/무거운 UIA 공급자, 또는 그 앱이 캐럿을 늦게 노출 | 가끔은 정상(첫 토글). 특정 앱에서 잦으면 그 앱의 접근성 응답이 느린 것 |
| `INDICATOR_UNREADABLE` | 작업 표시줄 입력 표시기를 오래 읽지 못함 | 대개 explorer 접근성 트리 병듦, 또는 입력기 1개/표시기 숨김 | 입력기 2개·표시기 노출 확인 → 여전하면 explorer 재시작([KNOWN-LIMITS](KNOWN-LIMITS.md)) |
| `UI_STALL` | UI 스레드가 프로브에 제때 답하지 못함(메시지를 펌프하지 못함) | UI 스레드가 무언가에 블로킹됨 → LL 키보드 훅이 멈춰 **시스템 전역 입력이 지연** | 로그의 `UI 스레드 응답 없음 (>=Nms)` 전후를 본다. 재현되면 제보 |

감시견 스레드가 500 ms마다 UI 스레드에 응답성 프로브를 보내고, 400 ms 안에 답이
없으면 `UI_STALL`을 기록한다 — 상시 타이머 없이 "입력 지연" 그 자체를 직접 잡는
신호다.

**제보(수동 번들)**: 트레이 → **이상 제보…**. 동의를 받은 뒤 자기완결 리포트
파일(환경·현재 상태·이상 요약·타임스탬프 찍힌 최근 로그)을
`%LOCALAPPDATA%\InputMethodIndicator\report-*.txt`에 쓰고, 그 파일을 선택한 채
폴더를 열며, 제목·본문이 채워진 GitHub 새 이슈를 브라우저로 연다. 리포트에는
**타이핑한 내용이 포함되지 않는다**(로그는 좌표·단계·앱 이름만 기록한다). 파일을
검토한 뒤 이슈에 첨부해 제출하면 순환이 닫힌다: **감지 → 수집 → 제보 → 진단**.

## 자주 나타나는 증상 읽기

| 증상 | 유력한 원인 | 확인할 곳 |
|---|---|---|
| 어디서도 한/영에 캡슐이 안 나옴 | 표시기를 못 찾음 | 상태 → `입력 표시기: 못 찾음` — 입력 방법 2개 이상인지, 표시기가 숨겨져 있지 않은지 확인 |
| 위와 같고, WARN 로그의 탐색 시간이 수십 초 | explorer 접근성 트리가 병듦 | 로그 → `표시기를 찾지 못했습니다/잃었습니다 (탐색 …ms)` — explorer를 재시작한다([KNOWN-LIMITS](KNOWN-LIMITS.md)의 "explorer 접근성 트리가 병듦" 참고) |
| 토글해도 `언어 변경 횟수`가 0에 머묾 | 워처가 요소를 보지 못함 | 표시기를 못 찾았거나, 파서가 모르는 한국어/영어가 아닌 UI 로케일 |
| 특정 앱에서만 캡슐이 안 나옴 | 그 캐럿을 찾지 못함 | Debug 로그 → `캡슐 생략 (캐럿을 찾지 못함)` ⇒ 그 앱이 접근성 캐럿을 노출하지 않음 |
| 앱을 시작한 뒤 **첫** 토글에서만 위치가 어긋남 | UIA 공급자가 아직 깨어나는 중이라 해석이 시간 초과됨 | Debug 로그 → `캐럿 단계=` 줄의 `…ms` 필드(예열된 공급자는 수십 ms에 답한다) |
| 두 번째 모니터에서 캡슐 크기가 잘못됨 | DPI | 상태 → DPI. 기하는 이로부터 스케일된다(렌더 타깃은 96에 고정) |
| 앱 전환 시 캡슐이 안 나옴(모드가 다름) | 설계상 그렇다 | 앱 전환 동기화는 유예 구간이 억제한다. 실제 토글만 보인다 |
| 포커스 표시기가 켜져 있는데 일부 필드에서 아무것도 안 나옴 | 텍스트 입력으로 인식되지 않음 | Debug 로그 → `캐럿 단계=` 줄의 `텍스트=0`, 또는 `포커스 캡슐 생략` |
